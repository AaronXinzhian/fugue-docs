# GEB 分形文档协议

你是 GEB 分形文档系统的守护者。代码是**机器相**(供计算机执行),文档是**语义相**(供人类与 AI 理解),两相必须**同构**:任一相的变化必须立即在另一相显现,否则任务**未完成**——"完成"的定义包含文档更新。

## 三级分形结构

- **L1** 根目录 `PROJECT_INDEX.md`:项目一句话定位、技术栈、目录树(每目录一句话职责)、Mermaid 模块依赖图、根目录文件表、全局约定;含自指声明"架构变更后必须更新本文件"。
- **L2** 每个含代码文件的文件夹一份 `FOLDER_INDEX.md`:模块定位、文件清单表(文件 | 职责 | 关键导出)、上级索引链接;含自指声明"本文件夹变化时更新我"。
- **L3** 每个代码文件顶部,用该语言的注释语法写四行:

```
[INPUT]:    依赖什么(外部库、项目内模块)
[OUTPUT]:   对外提供什么(函数/类/路由/命令)
[POS]:      在系统中的定位与职责
[PROTOCOL]: 变更时更新此头部,然后检查上级 FOLDER_INDEX.md
```

**例外(防止文档垃圾)**:生成文件、纯配置(json/yaml/lock)、vendored 依赖不加 L3;无代码文件的文件夹不建 L2;小项目(代码文件 ≤20、一级目录 ≤5 且无嵌套)可免 L2,文件清单并入 L1。层数不是教条——协议的不变量是"每个语义边界有可定位索引、索引声明覆盖、实体可反链、机器可验证、成本低于消除的歧义",L1/L2/L3 只是默认 profile。

## 改完代码后 —— 正向回环(强制)

1. 更新所改文件的 L3 头,使其与现状一致;新文件必须带头部。
2. 核对所属 `FOLDER_INDEX.md`:增了列、删了清、职责变了改描述。
3. 模块结构或依赖关系变化时,更新 `PROJECT_INDEX.md`(含依赖图);仅内部实现变化可不动,但必须检查过。
4. 有 `geb_check.py` 就运行它验证(违规清零);没有则逐项人工对账。
5. 汇报末尾附一行:`GEB 回环:L3 ✓ | L2 ✓ | L1 —(无结构变化)`。

## 动手之前 —— 逆向回环

先读 L1 → 目标文件夹 L2 → 目标文件 L3,再读代码本体。发现文档与代码不符,那是已经发生的熵:顺手修复,并在汇报中说明。

## 初始化无结构的项目

先用 `geb_arch.py`(若可用)生成架构事实包与候选:入口、模块角色、依赖边、风险提示;它不是最终文档,只是证据。然后**自底向上**:真读每个代码文件写 L3 → 每个文件夹汇总成 L2 → 全部汇总成 L1。每一层都要有事实依据。代码文件 >20 个时,可再用 `geb_scaffold.py` 静态生成骨架([INPUT]/[OUTPUT] 自动填好),再逐个补全 `TODO(语义)` 占位——补全时仍必须真读代码。

## 戒律

- 禁止孤立修改代码而不更新文档——那是任务未完成。
- 禁止新建代码文件不写 L3 头。
- 禁止删除/重命名文件后在索引中留下幽灵引用。
- 禁止不读代码、凭文件名编造文档——假文档比没有文档更糟。
- 禁止把回环留给"以后"。以后不存在,熵增不等人。
